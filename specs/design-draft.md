# Design draft: Redis Agent Memory as an n8n community node

_Last updated: 2026-11-04_

This is a draft, not a finished specification: it is the record of the research and the decisions behind `@redis/n8n-nodes-agent-memory`, and dated notes keep it current as the node changes.

It covers:

- why a dedicated node is worth building when n8n can already make HTTP requests;
- what n8n requires for verification;
- how comparable vendors have built their nodes;
- how Agent Memory's short-term and long-term memory fit n8n's memory model;
- how Agent Memory compares with plain Redis inside n8n workflows;
- how to run integration tests inside a real n8n, and how other community nodes do it.

## 1. Summary

- **What the node adds.** The value is not in wrapping the SDK. It is in things the HTTP Request node cannot do:
    - plugging into the AI Agent's **memory slot** (`ai_memory`);
    - exposing well-described **agent tools**;
    - a **credential type** with a connection test;
    - a guided UI.
- **No SDK in the package.** Verified nodes may not have runtime dependencies, so the package must not depend on `@redis-iris/agent-memory`. It calls the REST API directly through n8n's `httpRequestWithAuthentication` helper.
- **The memory sub-node is verifiable.** n8n's official **`@n8n/ai-node-sdk`** comes from the n8n host as a peer dependency, not a runtime dependency. Cognee, a verified vendor, already ships a memory sub-node built this way. The `n8n-node` CLI now has a `programmatic/custom-chat-memory` template for it, which this repo was scaffolded from.
- **Name.** `@redis/n8n-nodes-agent-memory`, with the repo at `github.com/redis/n8n-nodes-agent-memory`.
- **Positioning.** Plain Redis (the built-in Redis Chat Memory) is enough for short, single-conversation memory. Agent Memory is for:
    - memory that persists per user across conversations;
    - long threads kept coherent by summarization;
    - automatic fact extraction;
    - memory shared with non-n8n agents.
- **Testing.** n8n publishes no test harness for community nodes, and most vendor nodes have unit tests at best. The realistic option is a pinned `n8nio/n8n` container with the built package mounted, workflows seeded through the n8n CLI, and a stub OpenAI server for the model. Couchbase's node is the reference (§11). The repo has three layers, unit, contract and end-to-end; `../docs/testing.md` describes them.
- **Short-term vs. long-term.** n8n's memory slot is a chat-history contract for one session, so Agent Memory's short-term (session) memory fits it directly. Long-term memory does not: the slot gets no query, so recall needs a tool, a search step before the agent, or opt-in injection (§9). The node ships the first and the last: the action node as a tool, and a Recall Long-Term Memories switch on the memory sub-node.

## 2. The Agent Memory TypeScript SDK

`@redis-iris/agent-memory` (v0.3.1 when this section was written; MIT):

- **What it is.** A thin client generated by [Speakeasy](https://www.speakeasy.com/) from the Agent Memory OpenAPI spec. Its only dependency is `zod`.
- **Auth.** An HTTP bearer API key, read from the `apiKey` option or the `AGENT_MEMORY_API_KEY` environment variable. Calls are scoped by `serverURL` and `storeId`.
- **Recent changes (0.3.x).**
    - Namespace resources (`namespaceRef`) replace the deprecated flat `namespace` label.
    - A new HTTP 424 error type, `MemoryFailedDependencyErrorResponseContent`, signals that the memory or model-provider dependency failed.

_(2026-11-04: version 1.0.0 was published on 2026-11-04, after betas from 2026-10-21, with a new "unified Iris API" (read from the package's README and `dist/esm/funcs`). Data-plane paths move to `/iris/data/v1/agent-memory/stores/{storeId}/...`, with `sessions` and `memories` in place of `session-memory` and `long-term-memory`; search takes `query` and `minScore` instead of `text` and `similarityThreshold`; lists return `nextCursor`, sent back as `cursor` instead of `pageToken`; bindings and filters use `namespaceId` instead of `namespaceRef`; and a filter carries its own conjunction in `op` (`ALL` or `ANY`) instead of the request-level `filterOp`. The hosted store moved to the unified Iris API on 2026-11-04 and the node was ported the same day. The table and the paths quoted below describe the 0.3.x API the node was first built against and are kept as history; §14 lists what the new API offers beyond the port.)_

The SDK's operations map to these REST endpoints (0.3.x shapes):

| Area | Operation | REST |
|---|---|---|
| Health | `health`, `storeHealth` | `GET /health`, `GET /v1/stores/{storeId}/health` |
| Session memory | `addSessionEvent` | `POST /v1/stores/{storeId}/session-memory/events` |
| | `getSessionMemory`, `deleteSessionMemory` | `GET` / `DELETE /v1/stores/{storeId}/session-memory/{sessionId}` |
| | `getSessionEvent`, `deleteSessionEvent` | `GET` / `DELETE …/session-memory/{sessionId}/events/{eventId}` |
| | `listSessions` | `GET /v1/stores/{storeId}/session-memory` |
| Long-term memory | `searchLongTermMemory` | `POST /v1/stores/{storeId}/long-term-memory/search` |
| | `bulkCreateLongTermMemories`, `bulkDeleteLongTermMemories` | `POST` / `DELETE /v1/stores/{storeId}/long-term-memory` |
| | `getLongTermMemory`, `updateLongTermMemory` | `GET` / `PATCH …/long-term-memory/{memoryId}` |
| | `updateLongTermMemoryFields` | `PATCH …/long-term-memory/{memoryId}/fields` |
| | `moveLongTermMemories` | `POST …/long-term-memory/move` |
| Namespaces | `list`/`create`/`get`/`update`/`deleteNamespace` | `/v1/stores/{storeId}/namespaces[/{namespaceId}]` |

**Data model highlights:**

- **Session events.** Each event has `eventId`, `actorId`, `sessionId` and `role` (`USER` / `ASSISTANT` / `SYSTEM`). Its `content` is an array of `{ text }` parts, plus `createdAt` and optional `metadata`.
- **Session memory response.** Returns the retained `events` plus an optional **`summary`**: a compacted summary of older turns maintained by a background summarization job. Its fields are `text`, `summarizedUpToEventId` (the boundary: this event and all before it are covered; `events` holds the turns after it), `summarizedEvents`, `createdAt`, `updatedAt` and `metadata`. Observed on the hosted store (2026-11-02): after 40 events the server kept the last 20 and summarized the first 20, and the summary appeared about 20 seconds after the last write. A recorded response is in `../test/unit/fixtures/session-with-summary.json`.
- **Memory records.** Fields are `id`, `text`, `memoryType`, `sessionId`, `ownerId`, `namespaceRef`, `topics`, typed `attributes` (for custom memory types), `createdAt` and `updatedAt`.
- **Errors.** Every error is an RFC 9457 Problem Details body. The shapes, as verified against the hosted service, are in §2.1.
- **Search.** Semantic search over long-term memory with:
    - `similarityThreshold` (0–1) and `limit` (1–100);
    - filters on owner, session, namespace, topics, memory type and creation date, combined with an and/or `filterOp`;
    - paging via `pageToken`.

### 2.1 Error responses

Verified on 2026-11-02 against the docs' OpenAPI spec, the SDK (0.3.1 and 1.0.0-beta.1, `dist/esm/models/errors`), the docs' demo script (`redis/docs`, `static/js/agent-memory-demo.js`) and the hosted service, one request per case.

**Shape.** Every API error is an RFC 9457 Problem Details body: `type` (a problem URI such as `/errors/resource-not-found`), `title`, `status`, `detail`, and for 400s a `fields` array. The spec and both SDK versions define one 404 schema, `NotFoundErrorResponseContent`, whose `type` has the single value `/errors/resource-not-found`; the SDK matches 404 by status alone. The resource is named only in `title`. The 1.0.0-beta.1 SDK adds `gateway-not-found` and `upstream-not-found`, for other resources. The docs' quickstart, developer guide and overview say nothing about errors.

| Request | Answer |
|---|---|
| `GET …/session-memory/{missing}` | `404`, JSON: `{"type":"/errors/resource-not-found","title":"Session Not Found","status":404,"detail":"The requested session was not found"}` |
| `DELETE …/session-memory/{missing}` | `204`, no body |
| `GET …/long-term-memory/{missing}` | `404`, same shape, `title: "Memory Not Found"` |
| `GET …/namespaces/{missing}` | `404`, same shape, `title: "Namespace Not Found"` |
| Wrong Store ID, malformed or well-formed 32-hex, on `/health` or a session path | `403`, `text/html` nginx page; the request never reaches the API, so the key seems bound to its store |
| Server URL with an extra path segment (`/v1/v1/stores/…`) | `403`, `text/html` nginx page |
| Unknown path under a valid store | `404`, `text/plain` "404 page not found" |
| Event ID shorter than 32 characters, on an existing or a missing session | `400`, `/errors/invalid-data`, "EventID: the length must be exactly 32." |

**How n8n presents them.** `httpRequestWithAuthentication` wraps the axios error in a `NodeApiError` itself. That constructor keeps the parsed JSON body in `error.context.data`, takes `description` from the first of its known keys (`detail` comes before `title`), and sets `message` from the status code. A missing session therefore reads "The resource you are requesting could not be found" with the description "The requested session was not found". A text or HTML body leaves `context.data` unset; the nginx 403 reads "Forbidden - perhaps check your credentials?", which is apt, since the Store ID is part of the credential. Constructing a `NodeApiError` from a `NodeApiError` returns the original unchanged, so options such as `itemIndex` passed at that point are dropped.

**What the node does with this.** The shared request adapter (`../nodes/shared/agentMemoryRequest.ts`) treats a 404 as "does not exist" only when `context.data.type` is `/errors/resource-not-found`; any other 404 fails the run. It sets `context.itemIndex` by hand on errors n8n has already wrapped. The chat history's `clear()` keeps the same tolerance, although the live `DELETE` of a missing session is a 204 and never needs it. A contract test pins the `GET` body and the `204`.

_(2026-11-04: the adapter now also rewrites what the user sees. The scenario review of 2026-11-03 (§11.3) found that n8n's generic text hid every server reason, such as "SessionID: must contain only alphanumeric characters" or "state can only be ARCHIVED". For any body whose `type` starts with `/errors/`, `detail` becomes the error message and `title (HTTP status)` the description, so the editor and a model that calls the node as a tool both get the reason; the full body stays in `context.data`. A 403 without such a body is the gateway's, and gets a description that names the API Key, the Server URL and the Store ID, since the gateway refuses all three faults alike. The credential test has a matching 403 rule.)_

## 3. Why a community node, given the HTTP Request node exists

The SDK is a thin layer over REST. A node that only wraps CRUD calls would add little over the HTTP Request node. The real value is in n8n-specific integration points.

1. **The AI Agent's memory slot.** The AI Agent has a dedicated `ai_memory` input that only memory sub-nodes can connect to, not the HTTP Request node. Without a sub-node, users rebuild memory by hand in every workflow. A sub-node can:
    - on load, call `getSessionMemory` (optionally `searchLongTermMemory` too);
    - on save, call `addSessionEvent` for the user and assistant turns;
    - let the server handle long-term extraction asynchronously.
2. **Agent tools.** Operations like _Search long-term memory_ and _Save memory_ become agent tools (`usableAsTool`) with good names, descriptions and parameter schemas. This is possible today with the HTTP Request Tool, but the quality depends on each user's prompt engineering.
3. **A credential type.** Server URL, store ID and API key are set once, with a built-in test against the store health endpoint.
4. **A guided UI.**
    - Resource/operation dropdowns.
    - `loadOptions` for namespaces.
    - Pagination for `listSessions`.
    - Proper handling of hierarchical namespaces, steering users away from the deprecated `namespace` field.
5. **Error handling.** 409 (namespace conflicts or archived namespaces) and 424 (dependency failures) become readable n8n errors, with retries where they make sense.
6. **Discoverability and positioning.** The node appears in the node panel and the AI sub-node panel, which is a natural successor to `memoryRedisChat` as LangChain deprecates `RedisChatMessageHistory`.

_(2026-11-04: of points 4 and 5, the node ships resource and operation dropdowns, paging for every Get Many, and errors that quote the API's own reason (§2.1). It has no `loadOptions` for namespaces, no retries, and no special handling of 409 or 424 beyond that quoting; none has been missed in testing.)_

_(2026-11-04, later: the namespace list now ships, as a `listSearch` resource locator on the top-level Namespace fields of Namespace → Get, Update, Delete and Long-Term Memory → Move, rather than as `loadOptions`; the node matches a search string against the names itself, since the API has no name search. Every operation that returns records also gained n8n's Simplify switch, on by default.)_

## 4. n8n verification rules

Source: [Community Node Verification Guidelines](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/verification-guidelines.md). The old `/integrations/creating-nodes/build/reference/verification-guidelines/` URL now returns a 404.

1. **Use the `n8n-node` tool** to create and check the package (scaffolding, metadata, lint, local testing).
2. **Node types:**
    - No duplicates of existing nodes; improvements to an existing node should be pull requests.
    - No logic or flow-control nodes.
    - **One third-party service per package.**
    - Trigger nodes may accompany the main node.
3. **Package source checks:**
    - The npm `repository` URL must match a public GitHub repo, and its links must work.
    - Author and maintainer details must be consistent between npm and GitHub.
    - README with usage examples.
    - **MIT license.**
    - **Published from a GitHub Action with npm provenance.** Required for verification submissions from **1 May 2026**; needs `@n8n/node-cli` ≥ 0.23.0.
4. **No external (runtime) dependencies.** The build guide's wording is "verified community nodes aren't allowed to use any run-time dependencies".
5. **Documentation.** README or API docs covering usage, example workflows and authentication.
6. **No access to environment variables or the file system.** All inputs come through node parameters and credentials.
7. **n8n best practices.** TypeScript, error handling and validation, and a clean linter run.
8. **English only.** This covers parameter names, descriptions, help text, errors and the README.

**Packaging basics:**

- The name must be `n8n-nodes-<name>` or `@<scope>/n8n-nodes-<name>`.
- The `n8n-community-node-package` keyword is required.
- Nodes and credentials must be registered under the `n8n` attribute of `../package.json`.

**UX guidelines highlights** ([UX guidelines](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/ux-guidelines.md)):

- **Credentials and operations.**
    - Sensitive credentials are password fields.
    - Use CRUD vocabulary: Create, Create or Update, Delete, Get, Get Many, Update.
    - Use the Resource Locator, defaulting to "From list".
- **Output.**
    - Delete operations return `{"deleted": true}`.
    - Add a _Simplify_ toggle when a response has more than 10 fields.
    - AI tool nodes get an _Output_ parameter: Simplified / Raw / Selected fields.
- **Text conventions.**
    - Title Case for names; Sentence case for actions and descriptions.
    - Placeholders start with "e.g.".
    - Boolean descriptions start with "Whether…".
- **Errors.** Explain what happened and how to fix it, and include `[Item N]`. Avoid the words "error", "problem", "failure" and "mistake".

**Practical consequences for this package:**

- **Don't depend on `@redis-iris/agent-memory`** (rule 4). Also avoid bundling it: its environment-variable fallback could conflict with rule 6, and n8n's artifact scanner inspects bundled code (see the MongoDB thread in §6).
- **Don't depend on `@langchain/*`.** Couchbase's node was flagged for exactly this. Use `@n8n/ai-node-sdk` (§8) instead.
- **Expect a "duplicate" question** about the built-in Redis Chat Memory. The case for a separate node: a different service (Agent Memory rather than raw Redis), plus summarization, long-term memory and cross-session recall.

## 5. Naming

- **npm:** `@redis/n8n-nodes-agent-memory`.
    - `@redis` is Redis's own npm scope (`@redis/client`), which signals a first-party node and simplifies the author-consistency check.
    - The scope already says Redis, so the name doesn't repeat it.
    - "Agent Memory" matches the product name.
    - Alternatives:
        - `@redis-iris/n8n-nodes-agent-memory`: sits next to the SDK, but is less recognisable to n8n users.
        - `n8n-nodes-redis-agent-memory`: the fallback if nobody can publish under a scope.
- **GitHub:** `github.com/redis/n8n-nodes-agent-memory`. `repository.url` must point to this exact public repo, and the publish workflow must run from it, because provenance records the source repo.
- **Inside the package** _(revised 2026-11-02)_:
    - Action node: **"Redis Agent Memory"**, the plain product name. n8n and the verified vendors give the plain name to the action node and a qualified name to the memory sub-node ("Redis" / "Redis Chat Memory", "Postgres" / "Postgres Chat Memory", "Cognee" / "Cognee Memory"). It is one node with three resources and `usableAsTool`, so the earlier idea of a separate "Redis Agent Memory Tool" or "Search Agent Memory" tool node does not apply. n8n appends " Tool" to the display name of every `usableAsTool` node when it offers it in the Tool picker (`packages/cli/src/tool-generation/ai-tools.ts`), so the same node is listed there as "Redis Agent Memory Tool". That name must not be declared in code: `n8n-nodes-redgres` declares a node "Redgres Tool" and the picker shows "Redgres Tool Tool". Docs name the node as the screen does in each context: "Redis Agent Memory" for a workflow step, "Redis Agent Memory Tool" on the Tool input (decided 2026-11-03, after the README had used the action-node name for both faces).
    - Survey of community pairs (2026-11-03, display names read from the published `dist` files of 15 packages that ship both a memory sub-node and an action node, among them Mem0, Cognee, Hindsight, Supermemory, MemorySync, Recallio, Couchbase, MemMachine, Engram, Flair, Redgres): 12 give the action node the bare brand and the sub-node brand + "Chat Memory" (6) or brand + "Memory" (6); 3 give the action node a role word instead ("MemMachine Manager", "Engram Admin", "Flair Write"). No community package pairs a memory sub-node with an action node for a core provider (Redis, Postgres, MongoDB, Zep, Xata, Motorhead); the ones that extend a core provider qualify the core name ("Redis Chat Memory (Isolated)", "Postgres Memory+", "Zep Memory v3"). The current names were kept.
    - Memory sub-node: **"Redis Agent Chat Memory"**. It reads like its neighbours in the Memory slot picker ("Redis Chat Memory", "Postgres Chat Memory"), and "Agent" marks it as the Agent Memory product's. The first draft called both nodes "Redis Agent Memory", which put two identical entries in the main node search and in the tool picker, told apart only by their descriptions. The internal name stays `redisAgentMemoryChatMemory`. "Redis Agent Memory Chat Memory" would keep the full product name but is clumsy.
    - Credential: "Redis Agent Memory API" (`redisAgentMemoryApi`).
- **Before publishing:** publish rights on the `@redis` npm scope are needed. The current `@redis/client` maintainers can publish or grant access.

| Package | Vendor | Verified | Runtime deps | Notes |

MongoDB, Postgres and the existing Redis integrations ship inside n8n core (`n8n-nodes-base` / LangChain nodes) and never go through community verification.

**Database drivers can't be verified today.** A September 2026 thread on the n8n forum confirms that nodes needing a wire-protocol driver (the MongoDB driver requires `net`, `tls`, `dns`, `fs`) cannot pass verification:

- n8n staff wrote there is "currently no supported path".
- Bundling doesn't help, because the artifact scanner inspects the driver's internals.

Agent Memory is a REST API, so this doesn't affect this package. It would affect any node that talks to Redis directly.

**Built by third parties:**

- **Zep:** `n8n-nodes-zep-memory-v3` and several others. Memory sub-node; depends on Zep's cloud SDK.
- **Supermemory:** `n8n-nodes-supermemory`. Memory sub-node plus tool; no runtime dependencies.
- **Graphiti:** `n8n-nodes-graphiti`. Memory sub-node; depends on LangChain and others.
- **Self-hosted Mem0:** `n8n-nodes-mem0-self` plus about five other Mem0 forks.
- **Redis:** `n8n-nodes-memory-redis-isolated`. Redis chat memory with per-user isolation, built on `@n8n/ai-node-sdk`, but depends on `redis`.

**Takeaways:**

- Cognee is the reference implementation to copy: a verified vendor node with a memory sub-node and a tool node, zero dependencies, and the official AI SDK. Source: [topoteretes/cognee-integrations/integrations/n8n](https://github.com/topoteretes/cognee-integrations/tree/main/integrations/n8n).
- No database vendor has an official memory node, and there is no verified Zep or Mem0 memory sub-node. That is an opening for a first-party Redis node.
- **Caveat:** Cognee's _package_ is verified, but its memory sub-node only arrived in 0.7.0 (September 2026). Whether AI SDK-based sub-nodes pass review has not been confirmed with n8n.
- **How Cognee's memory sub-node works (read 2026-11-02).** On every agent turn it (1) loads the last _Window Size_ Q&A pairs from the session, (2) if _Recall Context_ is on, queries the knowledge graph with the incoming question and adds the result as one extra system message that is never written to the session, and (3) saves the user message and reply as one session entry. A fourth, periodic step, _Promote To Graph_ (every N hours, after each execution, or never), pushes session turns into the graph through the "improve" endpoint; without it long-term memory never changes. Its README states that the Chat Memory Manager's _Delete Messages_ and _Insert with Override All_ fail with an error, because clearing a session is not supported. The action node (`usableAsTool`) is attached to the Tool port for searches the agent chooses to run. Mem0's documented agent pattern is two instances of its action node on the Tool port, one pinned to _Search_ and one to _Add_, with _User ID_ a fixed parameter kept the same on both.

## 8. Building a memory sub-node: `@n8n/ai-node-sdk`

`@n8n/ai-node-sdk` is n8n's SDK for AI nodes. It is published from the n8n monorepo, has existed since February 2026, and was at 0.32.x at the time of writing.

**How it is wired in:**

- **Package setup.** Declare it as a **peer dependency**, alongside `n8n-workflow`, and set `"aiNodeSdkVersion": 1` in the `n8n` block of `../package.json`. n8n provides it at runtime, so the package keeps zero runtime dependencies.
- **Minimum n8n version.** 2.16, per Cognee's PR. _(2026-11-02: nothing tests that floor, so the README claims only what the end-to-end suite runs on, n8n 2.42.6, plus the nightly run on the latest release, and `peerDependencies['@n8n/ai-node-sdk']` is `>=0.32.4`. Widen the claim when an older image joins the e2e matrix.)_
- **Scaffolding.** The CLI generates the skeleton: `n8n-node new <name> --template programmatic/custom-chat-memory`.

The pattern, as used in this repo's `../nodes/RedisAgentMemoryChatMemory`:

```ts
class AgentMemoryChatHistory extends BaseChatHistory {
  getMessages()          // GET  /v1/stores/{storeId}/session-memory/{sessionId}
                         //      → events only; the summary stays out (§9.3)
  addMessage(message)    // POST /v1/stores/{storeId}/session-memory/events
  clear()                // DELETE /v1/stores/{storeId}/session-memory/{sessionId}
}

class SummaryAwareWindowedChatMemory extends BaseChatMemory {
  loadMessages()         // the same GET, plus POST …/long-term-memory/search when
                         // recall is on → recalled memories, summary, windowed events
}

// in supplyData():
const memory = new SummaryAwareWindowedChatMemory(history, { windowSize, includeSummary, recall });
return supplyMemory(this, memory);
```

_(The first sketch extended `WindowedChatMemory` and put the summary in `getMessages()`; the note below and §9.3 say why both changed.)_

HTTP calls go through `this.helpers.httpRequestWithAuthentication`, using the credential's `authenticate` block (a bearer header).

## 9. Short-term and long-term memory in n8n

This section maps Agent Memory's two kinds of memory onto the places n8n uses memory. The findings come from n8n's source (`master`, read 2026-10-09) and `@n8n/ai-utilities` 0.32.4, which `@n8n/ai-node-sdk` re-exports.

### 9.1 The two kinds of memory in Agent Memory

| | Short-term (session memory) | Long-term (memory records) |
|---|---|---|
| Unit | Ordered events: `role`, `content`, `actorId` | Facts: `text`, `memoryType`, `topics`, `attributes` |
| Key | `sessionId` | `ownerId` (a user), optionally a namespace |
| Lifetime | One conversation; older turns fold into a summary | Across all of a user's conversations |
| Read | `GET …/session-memory/{sessionId}` returns the summary and recent events | Semantic search with filters |
| Write | `POST …/session-memory/events` | Extracted by the server from session events, or created directly |

The two are linked. Each session event carries an `actorId` and optional `namespaceRef`, and the server extracts long-term memories from those events. **Writing short-term memory therefore writes long-term memory as a side effect.** Only reading long-term memory needs a separate path.

### 9.2 What n8n means by "memory"

n8n has one memory abstraction: the chat history of one session. Every node with an `ai_memory` input uses the same contract.

| Consumer | What it calls | When |
|---|---|---|
| AI Agent, memory slot | `loadMemoryVariables({})`, which returns `chat_history` | Before each run |
| | `saveContext({ input }, { output })`, or `chatHistory.addMessages([...])` when tools ran | After each run |
| Chat Trigger, "Load Previous Session: From Memory" | `chatHistory.getMessages()`, dropping messages marked `hideFromUI` | When the hosted chat widget opens |
| Chat Memory Manager | `chatHistory.getMessages()`, `clear()`, `addMessage()` | Load, Insert and Delete modes |
| OpenAI Assistant (v1) | `loadMemoryVariables` / `saveContext` | Before and after each run |

What the source shows about this contract:

1. **Loading gets no input.** The Agent's `loadMemory()` calls `memory.loadMemoryVariables({})`, and the SDK's `LangchainMemoryAdapter` ignores the argument anyway. A memory node cannot see the user's message through the call. It can still read it through a parameter: sub-node parameters resolve against the agent's input item, which is why `{{ $json.sessionId }}` works, and `{{ $json.chatInput }}` works the same way.
2. **Saving has two paths.** Without tool calls, the Agent calls `saveContext`, which reaches the SDK's `saveTurn(input, output)`. With tool calls, `saveToMemory()` skips `saveContext` and calls `chatHistory.addMessages()` with the full sequence: the user message, AI messages that carry tool calls, tool results, and the final answer.
3. **The Agent trims again.** With `maxTokensFromMemory` set, the Agent trims history by tokens and keeps system messages (`includeSystem: true`), so a leading summary survives. _(2026-11-04: this held while the summary was a system message. It is a user message now, because Anthropic and Gemini reject a system message after the Agent's own (§13, blockers), so a token trim can drop it with the oldest turns. Nothing tests that case; a generous `maxTokensFromMemory` is the workaround.)_
4. **One memory per consumer.** The Agent's and the Chat Trigger's memory inputs both have `maxConnections: 1`. An agent cannot use Redis Chat Memory for short-term memory and Agent Memory for long-term memory at the same time through the slot.
5. **SDK messages carry only role and content.** The SDK's message converter drops LangChain's `additional_kwargs`, so a node built on `@n8n/ai-node-sdk` cannot mark a message `hideFromUI`.
6. **Two layers, two entry points.** `supplyMemory()` wraps a `ChatMemory` (which has `loadMessages`) around a `ChatHistory` (which has `getMessages`). The Agent reads through `loadMessages`. The Chat Trigger and the Chat Memory Manager read `chatHistory.getMessages()` directly. So anything added in `loadMessages` reaches the model but not the chat widget or the Memory Manager.

### 9.3 Short-term memory fits the memory slot

The contract matches session memory almost one to one:

| n8n call | Agent Memory |
|---|---|
| `getMessages` | `GET …/session-memory/{sessionId}`: the events |
| `loadMessages` | the same, with the summary (and recalled long-term memories, §9.4) put first as user messages |
| `addMessage` / `saveTurn` | `POST …/session-memory/events`, one event per message |
| `clear` | `DELETE …/session-memory/{sessionId}` |

This is what the `RedisAgentMemoryChatMemory` node does. _(The first draft returned the summary from `getMessages` as a system message; the first bullet below and §13 record why it moved to `loadMessages` and became a user message.)_ It also fills a gap: n8n's earlier memory-server nodes, Zep and Motorhead, offered server-side summaries but are now deprecated and hidden from the node panel.

**Friction points, with fixes:**

- **The summary leaks into the chat widget.** The node adds the summary in `getMessages`, so the Chat Trigger returns it when the widget loads a previous session. The widget labels every message that isn't a `HumanMessage` as `bot`, so the summary appears as a bot reply, and the SDK cannot hide it (point 5). The widget also reads `kwargs.content` as text, but SDK messages carry an array of content blocks; rendering in the hosted chat needs a test. **Fix:** add the summary in `loadMessages` (the memory class), not in `getMessages` (the history class). Point 6 means the model still gets it and the widget does not. _(Done. An e2e test loads a previous session through the Chat Trigger, and an opt-in contract test waits for a real summary and checks that `loadMessages` has it and `getMessages` does not. The 2026-11-03 scenario review showed a 20 KB message with emoji, CRLF and JSON reaching the widget byte for byte, which answers the rendering question.)_
- **Chat Memory Manager's "Delete last N" rebuilds the session.** It reads all messages, calls `clear()`, then re-adds the rest one at a time. On Agent Memory that deletes the server summary, posts the summary back as a `SYSTEM` event, gives every event a new ID and timestamp, and may trigger extraction again, which risks duplicate long-term memories. "Insert" with "Override All" also calls `clear()`. **Fix:** the change above keeps the summary out of the re-added messages. Document "Delete last N" as unsupported; the action node's per-event delete is the safe alternative. _(2026-11-02: "Insert > Override All" is a delete and repost by design, so losing the summary and extracting from the new events is the intended result; only "Delete last N" misbehaves. Cognee's sub-node makes `clear()` throw, which blocks both operations; we cannot copy that because our `clear()` is the real "Delete > All", and the SDK's `ChatHistory` interface, with only `getMessages`, `addMessage(s)` and `clear`, gives the node no way to tell a rebuild from a delete followed by an insert. The README's "Chat Memory Manager" note records the outcome.)_
- **Tool-call messages become extra assistant events.** When tools ran, the AI messages that carry tool calls arrive through `addMessages` with role `assistant`. The node drops tool results but would store any text in those messages, including n8n's synthetic "Calling X with input: …". **Fix:** skip assistant messages that contain tool-call blocks. (Done. On n8n 2.42.6, the end-to-end tests show this message arriving with no text, so nothing extra was stored there; the filter guards the synthetic-message case and other versions.)
- **History is windowed three times.** The server keeps recent events and summarizes the rest, the node applies Context Window Length, and the Agent may trim by tokens. **Fix:** treat the server as the main control. Keep a generous default window and say in the parameter description that older turns live in the summary. _(2026-11-02: done. On the hosted store the server retained 20 events, so the old default of 10 interactions was exactly at the edge and anything lower would have dropped turns. The default is 50 interactions and the maximum 500. The parameter description and the README say that the server trims the session first, that the summary covers only the turns the server has dropped, and that the window should not be lower than the number of turns the server retains, or a turn can fall between the two.)_ _(2026-11-04: the value is validated. The editor caps the field, but an expression can resolve to `0`, `""` or `"abc"`, and `slice(-NaN)` or `slice(0)` then returned the whole history with no sign of it. An absent or empty option now means the default of 50; anything else must be a whole number of 1 or more, or `supplyData` throws a `NodeOperationError` that quotes the resolved value.)_
- **The session ID is not a user ID.** The Chat Trigger supplies a `sessionId`, which the hosted widget keeps per browser in `localStorage`, but no user identity. Long-term memory is keyed by user, so cross-session recall needs a stable user ID: from the embedded chat's `metadata`, or a Telegram or Slack user ID. If a workflow passes the session ID as the user ID, long-term memory still works, but only within that session. _(2026-11-02: a probe showed the server sets a session's `ownerId` from its first event and then accepts events from any actor, so multi-user sessions are allowed by design. The node therefore requires a User ID, takes no identity from the session, and offers an opt-in **Verify Session Owner** option, off by default so it behaves like the other memory nodes, which fails instead of mixing two users' turns. The README's "Who may read a session" paragraph says that the trigger, not the node, authenticates callers.)_ _(2026-11-04: the mismatch was a plain `Error`, so n8n blamed whichever node called `getMessages()`, the Chat Memory Manager or the Agent, with no item index. It is now a `NodeOperationError` on the memory node, with the item index and a description that says the server names a session's first writer its owner. For the same reason an empty Session ID or User ID now puts its hint in the message itself: n8n shows a sub-node failure as "Error in sub-node …", demotes the message to the description and drops the description.)_

### 9.4 Long-term memory does not fit the memory slot

Writes need nothing extra: they happen through extraction (§9.1). Reads need a query, and the slot has none (point 1). There are three ways to read long-term memory:

| Option | How it works | For | Against |
|---|---|---|---|
| **A. Agent tool** | The action node with `usableAsTool`, or a dedicated tool node. The agent calls _Search memory_ or _Save memory_ when it judges it useful. This is the Mem0 and Cognee pattern. | Searches only when useful. Explicit saves. Each call shows in the execution log. | Depends on the model choosing to call it. Adds a model round trip. |
| **B. Search before the agent** | The action node runs a search on `{{ $json.chatInput }}` before the agent, and the system prompt includes the results through an expression. | Plain n8n: explicit and easy to debug. | Wiring in every workflow. |
| **C. Injection by the memory node** | An opt-in "Recall Long-Term Memories" switch. In `loadMessages`, the node searches on a query parameter (default `{{ $json.chatInput }}`) and adds the results as one message ahead of the history (a user message as shipped, §9.5). | No wiring; works with any agent. | A search on every turn, which adds latency. The query is only the latest message. |

**Two rules for every option:**

- **The workflow sets the user ID; the model never does.** In tool mode, `ownerId` must be a fixed node parameter, not an argument the model fills in. Otherwise a prompt could read another user's memories.
- **Expect a short lag.** Extraction is asynchronous, so a fact said in this turn may not be searchable in the next one. The session history covers that gap.

Option C must live in `loadMessages`, for the same reason as the summary: the recalled facts then reach the model but never the chat widget, the Memory Manager or the session's stored events.

**What the references do (added 2026-11-02).** Cognee's verified memory sub-node implements option C today (_Recall Context_, see §7) and ships the action node as a tool for option A; Mem0 implements option A only, with one tool instance per operation. Agent Memory is better placed than Cognee for option C: extraction is server-side and automatic, so there is no promote step. Recall in `loadMessages` closes the loop on its own: turns go in through the memory slot, the server extracts facts, and the next conversation gets them back with no wiring. For option A, both references avoid "one tool does everything": the workflow author pins resource, operation and User ID per tool instance, and the model fills only the content fields (`query`, `text`, `topics`). Our tool descriptions should target two or three pinned shapes: _Search memories_, _Save memory_, and _Forget memory_.

### 9.5 Where each kind of memory lives in n8n

| | Short-term | Long-term |
|---|---|---|
| Agent Memory concept | Session memory | Memory records |
| n8n concept | Chat memory (`ai_memory`) | None built in; the nearest is a vector store with a retriever tool |
| Write path | Memory slot saves each turn | Server extraction from session events; _Save memory_ tool or action |
| Read path | Memory slot loads each run | Tool (A), search before the agent (B), or opt-in injection (C) |
| Key | `sessionId` | User ID (`ownerId`) |
| Built-in alternatives | Simple Memory; Redis, Postgres and MongoDB Chat Memory | Vector store nodes |

**Recommendation.**

1. Keep the memory sub-node for short-term memory, and apply the fixes in §9.3.
2. Ship the action node with `usableAsTool`, which covers options A and B, with _Session → Delete Event_ included: it is the supported way to trim a session (see §9.3, "Delete last N"), and _Long-Term Memory → Search / Create / Delete_ are the tool shapes for recall, "remember this" and "forget me". Document the Mem0 pattern: one tool instance per operation, User ID pinned.
3. Ship option C as an opt-in _Recall Long-Term Memories_ setting on the memory sub-node, off by default, modelled on Cognee's _Recall Context_: a query parameter defaulting to `{{ $json.chatInput }}`, results added in `loadMessages` only. _(Revised 2026-11-02: this was "add later"; the verified reference already does it, and Agent Memory needs no promote step.)_ _(2026-11-04: shipped, and moved. The switch, _Recall Query_ (default `{{ $json.chatInput }}`) and _Recall Limit_ (default 5, 1 to 100) are top-level parameters of the sub-node, not entries under Options. An Options entry the user never adds resolves to `undefined`, so with the first layout the switch alone searched nothing and said nothing; a top-level default is always evaluated. The search filters on the User ID and, when set, the Namespace ID, and sends no similarity threshold. The recalled texts go to the model as one user message headed "Long-term memories about the user, from earlier conversations:", before the summary and the recent turns.)_

## 10. Agent Memory vs. plain Redis in n8n workflows

Plain Redis in n8n gives the agent **storage**. Agent Memory gives it a **memory system**: it decides what to keep, compacts it and makes it searchable.

**What n8n users have with plain Redis today:**

- **Redis Chat Memory:** the last N messages of one conversation, stored as a list per session key with an optional expiry. Nothing carries over between sessions, and there's no search.
- **Redis Vector Store:** search over your own documents, but you build the pipeline yourself: chunking, embedding, upserting and deciding what to store.
- **Redis node:** raw commands; anything memory-like is hand-built.

**What Agent Memory adds:**

1. **Facts are extracted automatically.** Every chat turn is appended to the session, and the server pulls out lasting facts in the background. With plain Redis this needs an extra LLM step plus a vector upsert in every workflow.
2. **Long conversations are summarized.** A background job folds older turns into a summary, and `getSessionMemory` returns the summary plus the recent turns. Redis Chat Memory just cuts off old messages, so early context is lost.
3. **Memory works across conversations.** Long-term memories are tied to a user (`ownerId`), not a single session, so a new conversation can recall earlier ones.
4. **Search with filters.** Semantic search with a similarity cut-off and filters on owner, topic, memory type, namespace and date. This would otherwise be built by hand on the Redis Vector Store.
5. **Structure and scoping.** Hierarchical shared or private namespaces, custom memory types with typed attributes, and topic tags. This matters for multi-tenant n8n setups such as agencies.
6. **Memory that can be managed.** List, read, update, delete and move memories, which supports "forget me" requests, corrections and moderation. With Redis Chat Memory, workflows can only write.
7. **Memory shared beyond n8n.** The same store is reachable from Python, TypeScript and REST, so n8n agents and in-app agents can share user memory.

**Trade-offs:**

- **It's an extra service.** Users need an Agent Memory deployment (managed, or self-hosted on Redis) rather than a Redis connection string.
- **It costs model calls.** Extraction and summarization call a model provider, which is why the API has its own 424 error for provider failures.
- **Recall lags slightly.** Extraction is asynchronous, so a fact isn't searchable in the very next turn.
- **Users get less low-level control** than with raw Redis.

**Positioning.** Use Redis Chat Memory for short, single-conversation history, where it's cheap, fast and built in. Use Agent Memory when the agent must remember a user across conversations, stay coherent over long threads, or share memory with other applications. In node terms:

- the memory sub-node covers points 1–3 automatically;
- the action and tool node exposes points 4–7.

## 11. Integration testing

The goal is to test the node as users run it: installed in a real n8n, wired to an AI Agent, and talking to a real Agent Memory store. The findings come from n8n's source (`master` and tag `n8n@2.42.6`), npm, and the repos of 23 community node packages, all read on 2026-10-09.

### 11.1 What n8n provides

n8n publishes **no test harness** for community nodes:

- **`NodeTestHarness`** (`packages/core/nodes-testing/`) runs workflow JSON in-process with `nock`. It is how n8n tests its own Agent with Simple Memory (`nodes/agents/Agent/test/integration/agent-v3.workflow.test.ts`). It is not in the `n8n-core` npm tarball, and it imports `../dist/...` paths inside the monorepo. Using it would mean copying and patching about seven files.
- **Test containers** (`packages/quality/environments/containers/`) and the Playwright suite are private packages. The `n8n-containers` package on npm belongs to an unrelated publisher; don't use it.
- **`@n8n/node-cli` templates have no tests**, including the memory template this repo came from.
- **n8n's own memory nodes** have only mocked unit tests that call `supplyData` with a stub context. `MemoryRedisChat` has no tests at all.

What n8n does provide is a **stock Docker image and a CLI**, and those are enough:

- **Loading the node.** At boot, n8n scans `~/.n8n/nodes/node_modules` for `n8n-nodes-*` and `@*/n8n-nodes-*` packages and needs no database record. Node types are package-qualified (`@redis/n8n-nodes-agent-memory.<nodeName>`), as in a real install. Peer dependencies (`@n8n/ai-node-sdk`, `n8n-workflow`) resolve from n8n itself, as long as the mounted package has no `node_modules` of its own.
    - `N8N_CUSTOM_EXTENSIONS` and `~/.n8n/custom` also work, and `n8n-node dev` uses them, but node types then become `CUSTOM.<nodeName>`. That differs from production.
- **Seeding.** `n8n import:credentials` takes plain, unencrypted credential data and encrypts it with `N8N_ENCRYPTION_KEY`. `n8n import:workflow` imports workflows, and `n8n publish:workflow --id=<id>` activates them. `--activeState=fromJson` fails in regular mode: it works only in queue or multi-main mode. None of these needs an owner account or API key.
- **Running.** `n8n execute --id=<id> --rawOutput` runs a workflow that starts with a Manual Trigger and prints the run as JSON. It exits 1 on failure. `--file` no longer works; import first. Set `N8N_LOG_LEVEL=error` so log lines don't mix with the JSON.
- **The Chat Trigger** answers `POST /webhook/<webhookId>/chat` on an active workflow with `public: true`:
    - `{ action: 'sendMessage', sessionId, chatInput }` runs the workflow. With `responseMode: 'lastNode'` it returns `{ output }`.
    - `{ action: 'loadPreviousSession', sessionId }` returns the memory's `getMessages()` when `loadPreviousSession` is `memory`. This is the path that exposes the summary leak in §9.3.
- **Owner account, if REST access is needed.** `N8N_INSTANCE_OWNER_MANAGED_BY_ENV=true` with `N8N_INSTANCE_OWNER_EMAIL` and a bcrypt `N8N_INSTANCE_OWNER_PASSWORD_HASH` creates the owner at boot. An API key then comes from `POST /rest/login` and `POST /rest/api-keys`. No environment variable seeds an API key, and the public API has no "run workflow" endpoint.
- **A fake model.** No fake chat-model node ships. Two options exist:
    - Point the `openAiApi` credential's `url` at a stub server that answers `/v1/chat/completions`. The stub can also record what the agent sent, which proves the history reached the model.
    - n8n's own Playwright tests use a LangChain Code node that returns a fake model from `@langchain/core/utils/testing`. The Tools Agent needs a model with `bindTools`, so use `FakeListChatModel`, not `FakeChatModel`. This option cannot show what the model received.

The findings, and what closed each:

- **Defects.** (F1) n8n's generic text hid every server reason: the adapter now quotes Problem Details (§2.1). (F2) Search with _Filter Match_ = Any returned other users' memories, because the API applies one conjunction to every filter field, the owner included: _Filter Match_ is gone, Search sends no `filterOp`, a `filterOp` left in a saved workflow is ignored, and a result owned by another user is refused rather than passed on. (F3) The recall switch alone did nothing: recall moved to the top level (§9.5). (F4) Nesting a namespace never succeeded, because the node sent `scope` with `parentId`: a child now sends only name and parent. (F5) Session → Get Many without a filter failed: it sends `includeAll=true`. (F6) Long-Term Memory → Get Many without a filter failed on the server: the node refuses it first and names the filters the API accepts. (F7) Update with no fields reached the server as an empty body: refused first, for memories and namespaces. (F8) A _Created At_ that is not a date gave a bare `Invalid time value`: validated, and the error names the field. (F9) Namespace → Update → _State_ offered "Active", which the API never accepts: an _Archive_ switch replaces the dropdown.
- **Usability.** (F10) _Max Results_ from an expression bypassed the editor's cap: validated as 1 to 100, and _Limit_ as 1 or more. (F11) The hint for an empty Session ID or User ID was dropped under the Agent: it is in the message (§9.3). (F12) The Chat Memory Manager with Simplify Output returns content parts, not strings, because the SDK's converter builds the messages: **open**, to report upstream. (F13) _Context Window Length_ from an expression turned the window off: validated (§9.3). (F14) Continue-on-fail items carried only n8n's text: F1 improves them. (F15) Create with an existing Memory ID overwrote without a word: the field says so. (F16) Every gateway 403 read as a key problem: the description names URL, store and key (§2.1). (F17) The README understated what _Delete Messages → Last N_ does: it now says the kept turns get new IDs and the deleting user becomes the owner. (F18) An owner mismatch was blamed on the calling node: it is a `NodeOperationError` on the memory node (§9.3). (F19) A Search or Get Many tool with no hits handed the model `""`: as a tool, the node returns `{ message: 'No memories matched' }`. A PERSONAL namespace without a User ID, one of F1's cases, is also refused before the request.

### 11.4 Test environment for Agent Memory

Contract and end-to-end tests run against a **hosted Agent Memory service**, not a local container. Redis runs a QA deployment for this. The test harness supplies the connection through environment variables. The names follow the SDK's `AGENT_MEMORY_API_KEY`:

| Variable | Credential field | Purpose |
|---|---|---|
| `AGENT_MEMORY_SERVER_URL` | `serverUrl` | Base URL of the service |
| `AGENT_MEMORY_STORE_ID` | `storeId` | Store the tests write to |
| `AGENT_MEMORY_API_KEY` | `apiKey` | Bearer API key |

**Rules:**

- **Only the harness reads these variables, never the node.** Verified nodes may not read environment variables (§4, rule 6). The harness writes them into the credential fixture before `n8n import:credentials`, and passes them to contract tests as constructor options.
- **Keep the URL and key out of the repo.** In CI they are repository secrets. Locally they come from an uncommitted `../.env` file, which `.gitignore` must list.
- **Skip without them.** If any variable is missing, the contract and end-to-end tests skip with a clear message, as Couchbase does for its OpenAI key. Pull requests from forks get no secrets, so for them only unit tests run.
- **Isolate each run.** The store is shared across runs and developers. Each run uses a unique prefix (for example `it-<run id>-`) for session IDs and user IDs, and deletes what it created at the end: `DELETE` each session, then bulk-delete the long-term memories owned by the test users. Concurrent CI jobs then don't see each other's data.
- **Allow for extraction lag.** Long-term memories appear asynchronously and cost model calls on the server. Tests that check extraction poll with a timeout, and there should be few of them. Most tests check session memory, which is synchronous.

### 11.5 Behaviours verified end to end

The scenario suite of 2026-11-03 (§11.3, 2026-11-04 status) confirmed these behaviours of the server and of n8n 2.42.6. None needs a change in the node; they are recorded here because the design in §9 relies on them. The tests that still pin them are in `../test/e2e`; [`testing.md`](testing.md) says how the design was verified.

- The server records the first writer as a session's `ownerId` and accepts events from any actor after that. Two users who send the same session ID share one session, and the second user's model request contains the first user's turns. This is what the README documents and what Verify Session Owner guards against (§9.3).
- Unscoped recall returns the user's memories from every namespace and from none; recall scoped to a namespace returns only that namespace's. `GET /session-memory/{id}` exposes `namespaceRef { namespaceId, name, path }` and `namespaceScope` for a bound session.
- Session → Add Event returns the event alone; the namespace binding shows only through Session → Get.
- Deleting a missing session answers 204, so the node reports `deleted: true`; deleting a missing namespace is a 404. The two resources differ, and the node passes each through as is.
- `DELETE /long-term-memory` lists every requested ID under `deleted`, existing or not, so the node's "was not deleted" check never fires against the current server. It stays as a guard.
- Long-Term Memory → Create returns what it sent, not the stored record: no `createdAt`/`updatedAt`, and no server default such as `memoryType: 'semantic'`.
- A 20 KB message with emoji, CRLF and JSON survives store, model replay and the chat widget byte for byte. Stored SYSTEM events reach the model as `user` messages, and the AI Agent 3.1 with empty options sends no system message of its own.
- The Chat Memory Manager handles items in order and stops at the first failure: with a bad second item, item 1 is stored, items 2 and 3 are not, and the error carries `itemIndex: 1`.
- With both a tool and the memory sub-node attached to one Agent, the sub-node shows two `loadMemoryVariables` runs per turn in the execution's run data. That is n8n's doing and has no visible effect.

## 14. Future work: what the unified Iris API adds

The port of 2026-11-04 kept the node's feature set and changed only the wire format. The new API (SDK `@redis-iris/agent-memory` 1.0.0, data plane under `/iris/data/v1/agent-memory/stores/{storeId}`) also offers endpoints and parameters the node does not use yet. This list was drawn up during the port, from the SDK's `dist/esm/funcs` and `models`, and is kept here so a later release can pick from it. Nothing below is committed to; each item names what an n8n user would gain.

**Small additions to existing operations**

- **Sort order on lists.** Sessions (`sortBy`: `sessionId`, `createdAt`, `updatedAt`; `sortOrder`: `ASC`, `DESC`), namespaces (`sortBy`: `id`, `name`, `createdAt`, `updatedAt`) and filter-only memory search (`sortBy`: `createdAt`, `updatedAt`; not with `query`). Today the node takes the server's default order. A _Sort_ option on the three Get Many operations would let a workflow fetch "the newest N" without reading everything.
- **Session list filtered by namespace.** `GET /sessions?namespaceId=` can combine with `ownerId`. Session → Get Many could offer a Namespace filter next to User ID.
- **Richer memory filters.** The filter object now takes `ne`, `in` and `all` on `sessionId`, `ownerId`, `topics` and `memoryType`; `createdAt` ranges (`gt`, `gte`, `lt`, `lte`, `eq`); typed `attributes` clauses (`{ string }`, `{ number }`, `{ boolean }`, `{ list }`); `unnamespaced: true`; and `excludeDocumentManaged`. Search and Get Many expose `eq`/`in` only. A date range and a topics "all of" would be the most used; `attributes` matters once custom memory types are in play.
- **Filter conjunction, carefully.** `filter.op: ALL | ANY` replaces the old request-level `filterOp`. The node dropped the option on purpose because `ANY` would OR the User ID away (§9.4, `ownedBy`). If it returns, it must apply to the other fields only, with the owner kept as a fixed `AND`; the API cannot express that in one filter, so it would mean a second client-side pass or no option at all.
- **Optimistic concurrency.** Memory records carry an opaque `revision`; `PATCH` and `PUT` accept `expectedRevision` and answer `412 /errors/revision-conflict` with `currentRevision`. Update could take an _Expected Revision_ field for workflows that read, decide and write. Simplified output would then need to expose `revision`.
- **Many IDs per call.** `POST /memories` creates up to 100 records and `POST /memories/bulk-delete` and `/memories/move` take up to 100 IDs; the node sends one per input item. A _Create Many_ or a _Delete Many_ that batches an input list would cut request counts for imports and clean-ups. The per-item error shape is now Problem Details (`memoryId`, `type`, `title`, `status`, `detail`), so partial failures can be reported item by item.
- **Explicit session creation.** `POST /sessions` creates a session and refuses an existing ID with `409 Session Already Exists` (`existingId` in the body). Append still creates on first event, so the node did not need it; a Session → Create operation would give workflows a "fail if it exists" guard.
- **Field-level update.** `PATCH /memories/{id}/fields` (worker-style: `memoryType` must match the stored type, `namespaceId` omission asserts "no namespace", `text` and `attributes`). Only useful once `attributes` are exposed.

**New resources**

- **Memory sources and evidence.** A memory can link to the session events or document revisions it came from: `GET /memories/{id}/sources`, `GET /memories/{id}/sources/{sourceId}/evidence`, and the reverse `GET /sources/{sourceId}/memories`. Records carry `sources`, `sourcesNextCursor` and `documentManaged`. For an agent this is "why do you believe that?"; for an operator it is an audit trail. A _Get Sources_ operation on Long-Term Memory is the natural first step.
- **Namespace routing policy.** `GET | PUT /namespace-routing` sets store-wide `ACCEPT`/`REJECT` rules that place long-term memories in shared namespaces; Move without `namespaceId` then auto-routes. Worth a Namespace → Get Routing / Set Routing pair for admins, and an _Auto-route_ switch on Move.
- **Document ingestion (MemoryETL).** `POST /document-ingestions` (202) takes a base64 document and extracts memories from it before any session exists; `GET /document-ingestions/{id}` reports status and `GET …/{id}/outputs` lists the memories produced. This is a classic n8n use: a file arrives, a workflow ingests it, the agent knows it. It needs a document Extractor configured on the store (control plane) and a polling pattern in n8n for the asynchronous status.
- **Summary views.** `GET | POST /summary-views`, `GET | PATCH | DELETE /summary-views/{viewId}`, `POST …/refresh` (202), `GET …/result`: server-materialized summaries of long-term memories, private or `SHARED`, filtered by namespace and grouped by owner, session, namespace or memory type, as text or structured output, refreshed on demand or continuously. Must be enabled on the deployment. A _Get Summary View Result_ operation would give an agent a standing briefing on a user or a topic in one call.
- **Ingestion hook status.** `GET /ingestion-hook-events[/{eventId}]` reports what a store's input hooks did with a write. Related: writes can now answer `422 /errors/ingestion-hook-stopped` (with `state`: `REJECTED`, `FAILED`, `EXPIRED`, `CANCELLED`, `CONFLICT`) and `503 /errors/ingestion-hook-retry` (with `retryAt`). The node renders both through the generic Problem Details path; a hook-aware retry (wait until `retryAt`, then resend with the same `idempotencyKey`, which every write already carries) is the piece that would make hook-enabled stores pleasant to use.
- **Health, unauthenticated.** `GET /iris/data/v1/agent-memory/health/live` and `/health/ready` need no key. Not useful to a workflow, but a cheaper probe for the credential test's "is the Server URL right" half.

**Control plane**

- The SDK now ships a second client, `AgentMemoryService`, for `/iris/v1/agent-memory/...`: stores, extractors, memory types (`memory-types`, `memory-types/reference`), detectors, models, metrics, `clear` (store wipe), databases and the EULA; several are marked cloud-only. It uses a different credential (an admin token or operator JWT), and the cloud control plane does not yet accept a programmatic credential. A separate credential type and an admin-flavoured node are conceivable, but not until the cloud side issues tokens; registering a custom memory type is the one call users have asked for.

**Not planned**

- A second node version that speaks the 0.3.x API. No server answers it any more (§12).
- Exposing `idempotencyKey` in the UI. The node generates one per write; a user-supplied key only matters for cross-run deduplication, which n8n workflows rarely need.

### 14.1 Where to focus: research of 2026-11-05

Four research threads ran in parallel on 2026-11-05 to rank the list above by what would matter to n8n users, not by what the API happens to offer: (a) what the competing memory integrations expose inside n8n; (b) what the n8n ecosystem itself reports as missing (forum, GitHub issues, tutorials that work around gaps); (c) how the memory vendors position themselves and where demand shows up in their issue trackers and in the literature; (d) what the n8n template library actually builds with memory, from a sample of 1,197 of the 1,275 templates that mention it. Counts, dates and links are in the source list at the end of this subsection; weak evidence is flagged where it is used.

**What the ecosystem builds and complains about**

- 86% of memory templates use a sliding window only (Simple Memory 1,030 of 1,197). Long-term memory is hand-built: Google Sheets in 222 templates, Postgres 140, Supabase 93, Pinecone 74, Google Docs 34, Airtable 33, each with 20–100 extra nodes and a "Save Memory" tool the model often never calls (forum 76880, 163582). Dedicated memory services barely register: Zep 1 template (built-in node deprecated since n8n 1.108.0), Mem0 0, Cognee 4 (vendor authors). The top long-term-memory template (2872, Google Docs, 58k views) and the top tutorials (133k, 77k, 44k views) all do what the shipped chat memory already does: extract facts per user and recall them per turn.
- The most-voted asks are for exactly this class of node: "Mem0 Memory node" 36 votes, "Mem0 integration" 31, "MemMachine node" 15; GitHub #39105 (cross-workflow memory with provenance). The single most-voted *bug* is n8n-side: the Agent writes every tool output into memory (#14361, 57 comments, 29 👍; #22112; forum 301833). This node already skips tool calls and tool results when it stores a turn, which is worth saying out loud.
- Ranked gaps that the shipped node does not close yet, by evidence weight: **session lifecycle** (reset, expire idle, purge all, list a user's sessions; threads with 6,900 / 5,735 / 4,774 views); **shared memory between agents without bleed** (7 threads, 2,508 views on the top one; multi-channel sales agents of 58–84 nodes); **documents kept current** (vector upsert hacks, 3,839 views, 21 posts, a team-acknowledged Pinecone bug); **corrections, supersession and audit** ("Berlin → Madrid", memory poisoning FR 296349, timestamps FR 57526 with 7 votes, rising through 2026); **human-readable summaries** (hand-off notes, weekly digests; the best hand-off template, 3350 with 17.9k views, has the human type the summary); **bulk import of history** (3,303 and 2,268 views).

**What competitors expose in n8n, and what the market treats as premium**

- Inside n8n, only Redis and Cognee ship both a chat-memory sub-node and a full action node from the vendor. Nobody exposes provenance to a workflow; nobody exposes routing rules; nobody exposes scheduled or shared summaries (Supermemory's community node has a single per-user `Profile Get`). Document/file ingestion is exposed by Cognee (binary file) and Supermemory (upload, URL, chunks, processing status); rich filters, sort and bulk by Supermemory's community node (24 downloads last month). Only Cognee is verified on n8n Cloud. Engram (AGPL, 2026-11-03) ships the only memory *trigger* node.
- In the wider market, per-user profiles and consolidation are now common premium features (Supermemory Profiles, Honcho representations, Zep context block, Mem0 Profiles beta); shared, grouped, structured views refreshed on demand are matched only by Hindsight's "mental models". Provenance is shipped unevenly (Zep episodes, Honcho Evidence, Hindsight citations, Cognee relational store) and absent from Mem0, Letta, LangMem, AgentCore, OpenAI and Anthropic; Mem0 carries three open 2026 feature requests for exactly what `…/sources` and `…/evidence` return (#7047 "which message produced this memory… did the model invent it… delete every memory derived from this document", #7624, #7782), and two 2026 benchmarks (HaluMem, STALE) name untraceable and stale memories as the core failure mode. Rule-based routing into shared namespaces, inbound ingestion hooks and optimistic concurrency are rare everywhere. Document ingestion is table stakes among premium products. What Redis lacks and cannot claim: graph relations, temporal validity, multimodal input, SaaS connectors, outbound webhooks.

**Recommendation**

Build in this order, and lead the story with the first two, which no other n8n integration offers and which the ecosystem is asking for in its own words:

1. **Summary views.** Smallest work for the largest number of flows (hand-off, digest, scheduled agents, cost), and a clean "finally" against every competitor node. Ship Get Result and Refresh first; the Schedule Trigger does the rest.
2. **Memory sources and evidence.** The one theme where demand is visible (Mem0's three open requests, the n8n forum's audit and poisoning threads, the 2026 benchmarks) and the incumbents are behind. Pair Get Memories for Source with bulk delete so "forget everything from this document or thread" is one step.
3. **Filters, sort, bulk create and delete, explicit session create.** Cheap, table stakes, and they close the most-viewed operational threads (session lifecycle, backfill, "forget me").
4. **Document ingestion with ingestion status.** Catch-up on paper, but in n8n it collapses the three most-copied flows after the personal assistant (knowledge base, transcripts, email). Be plain in the docs that it extracts facts and does not replace vector RAG for long documents, and that the Extractor is configured outside n8n.
5. **Governed shared memory: routing policy, Expected Revision, hook-aware retry.** Differentiated, but the demand is diffuse and the users are platform teams rather than template authors; sequence it behind 1–4 and market it to the multi-agent crowd (threads 81084, 246244, 4508).
6. **Later or blocked:** custom memory types (control-plane credentials), a memory trigger node (new node type; also needs the server to emit events), outbound webhooks (a server ask, not a node ask).

Positioning to state now, without building anything: the node already does what the top tutorials build by hand (per-user fact extraction and per-turn recall), already skips tool calls when storing turns (the most-voted n8n memory bug), owns the window and summary on the server (so the Postgres/Mongo window and tool-pair truncation bugs cannot occur), and exposes sessions, events, namespaces and Move, which no competitor node does. Verification on n8n Cloud matters more than any single feature: only Cognee has it among the long-term-memory vendors.

Evidence quality: forum view counts are page views; template node counts include sticky notes and the "after" counts are estimates; Reddit was unreachable, so it contributes nothing; Mem0 and Cognee template entries come from vendor-affiliated authors; GitHub title-search counts are noisy and were used only as direction. One side finding: the npm downloads API returned "not found" for `@redis/n8n-nodes-agent-memory` on 2026-11-05; the package is on the registry (0.2.0, published 2026-11-04), the downloads index just lags a new package by a day or so, so adoption numbers are not yet available.
