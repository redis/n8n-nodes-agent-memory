# Research: Redis Agent Memory as an n8n community node

_Last updated: 2026-10-09_

This document records the background research behind `@redis/n8n-nodes-agent-memory`:

- why a dedicated node is worth building when n8n can already make HTTP requests;
- what n8n requires for verification;
- how comparable vendors have built their nodes;
- how Agent Memory compares with plain Redis inside n8n workflows.

## 1. Summary

- **What the node adds.** The value is not in wrapping the SDK. It is in things the HTTP Request node cannot do:
  - plugging into the AI Agent's **memory slot** (`ai_memory`);
  - exposing well-described **agent tools**;
  - a **credential type** with a connection test;
  - a guided UI.
- **No SDK in the package.** Verified nodes may not have runtime dependencies, so the package must not depend on `@redis-iris/agent-memory`. It calls the REST API directly through n8n's `httpRequestWithAuthentication` helper.
- **The memory sub-node is verifiable.** n8n's official **`@n8n/ai-node-sdk`** comes from the n8n host as a peer dependency, not a runtime dependency. Cognee, a verified vendor, already ships a memory sub-node built this way. The `n8n-node` CLI now has a `programmatic/custom-chat-memory` template for it, which this repo was scaffolded from.
- **Name.** `@redis/n8n-nodes-agent-memory`, with the repo at `github.com/redis/n8n-nodes-agent-memory`.
- **Positioning.** Plain Redis (the built-in Redis Chat Memory) is enough for short, single-conversation memory. Agent Memory is for:
  - memory that persists per user across conversations;
  - long threads kept coherent by summarization;
  - automatic fact extraction;
  - memory shared with non-n8n agents.

## 2. The Agent Memory TypeScript SDK

`@redis-iris/agent-memory` (v0.3.1 at the time of writing; MIT):

- **What it is.** A thin client generated by [Speakeasy](https://www.speakeasy.com/) from the Agent Memory OpenAPI spec. Its only dependency is `zod`.
- **Auth.** An HTTP bearer API key, read from the `apiKey` option or the `AGENT_MEMORY_API_KEY` environment variable. Calls are scoped by `serverURL` and `storeId`.
- **Recent changes (0.3.x).**
  - Namespace resources (`namespaceRef`) replace the deprecated flat `namespace` label.
  - A new HTTP 424 error type, `MemoryFailedDependencyErrorResponseContent`, signals that the memory or model-provider dependency failed.

The SDK's operations map to these REST endpoints:

| Area | Operation | REST |
|---|---|---|
| Health | `health`, `storeHealth` | `GET /health`, `GET /v1/stores/{storeId}/health` |
| Session memory | `addSessionEvent` | `POST /v1/stores/{storeId}/session-memory/events` |
| | `getSessionMemory`, `deleteSessionMemory` | `GET` / `DELETE /v1/stores/{storeId}/session-memory/{sessionId}` |
| | `getSessionEvent`, `deleteSessionEvent` | `GET` / `DELETE …/session-memory/{sessionId}/events/{eventId}` |
| | `listSessions` | `GET /v1/stores/{storeId}/session-memory` |
| Long-term memory | `searchLongTermMemory` | `POST /v1/stores/{storeId}/long-term-memory/search` |
| | `bulkCreateLongTermMemories`, `bulkDeleteLongTermMemories` | `POST` / `DELETE /v1/stores/{storeId}/long-term-memory` |
| | `getLongTermMemory`, `updateLongTermMemory` | `GET` / `PATCH …/long-term-memory/{memoryId}` |
| | `updateLongTermMemoryFields` | `PATCH …/long-term-memory/{memoryId}/fields` |
| | `moveLongTermMemories` | `POST …/long-term-memory/move` |
| Namespaces | `list`/`create`/`get`/`update`/`deleteNamespace` | `/v1/stores/{storeId}/namespaces[/{namespaceId}]` |

**Data model highlights:**

- **Session events.** Each event has `eventId`, `actorId`, `sessionId` and `role` (`USER` / `ASSISTANT` / `SYSTEM`). Its `content` is an array of `{ text }` parts, plus `createdAt` and optional `metadata`.
- **Session memory response.** Returns the retained `events` plus an optional **`summary`**: a compacted summary of older turns maintained by a background summarization job (`summarizedUpToEventId`, `summarizedEvents`).
- **Memory records.** Fields are `id`, `text`, `memoryType`, `sessionId`, `ownerId`, `namespaceRef`, `topics`, typed `attributes` (for custom memory types), `createdAt` and `updatedAt`.
- **Search.** Semantic search over long-term memory with:
  - `similarityThreshold` (0–1) and `limit` (1–100);
  - filters on owner, session, namespace, topics, memory type and creation date, combined with an and/or `filterOp`;
  - paging via `pageToken`.

## 3. Why a community node, given the HTTP Request node exists

The SDK is a thin layer over REST. A node that only wraps CRUD calls would add little over the HTTP Request node. The real value is in n8n-specific integration points.

1. **The AI Agent's memory slot.** The AI Agent has a dedicated `ai_memory` input that only memory sub-nodes can connect to, not the HTTP Request node. Without a sub-node, users rebuild memory by hand in every workflow. A sub-node can:
   - on load, call `getSessionMemory` (optionally `searchLongTermMemory` too);
   - on save, call `addSessionEvent` for the user and assistant turns;
   - let the server handle long-term extraction asynchronously.
2. **Agent tools.** Operations like _Search long-term memory_ and _Save memory_ become agent tools (`usableAsTool`) with good names, descriptions and parameter schemas. This is possible today with the HTTP Request Tool, but the quality depends on each user's prompt engineering.
3. **A credential type.** Server URL, store ID and API key are set once, with a built-in test against the store health endpoint.
4. **A guided UI.**
   - Resource/operation dropdowns.
   - `loadOptions` for namespaces.
   - Pagination for `listSessions`.
   - Proper handling of hierarchical namespaces, steering users away from the deprecated `namespace` field.
5. **Error handling.** 409 (namespace conflicts or archived namespaces) and 424 (dependency failures) become readable n8n errors, with retries where they make sense.
6. **Discoverability and positioning.** The node appears in the node panel and the AI sub-node panel, which is a natural successor to `memoryRedisChat` as LangChain deprecates `RedisChatMessageHistory`.

## 4. n8n verification rules

Source: [Community Node Verification Guidelines](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/verification-guidelines.md). The old `/integrations/creating-nodes/build/reference/verification-guidelines/` URL now returns a 404.

1. **Use the `n8n-node` tool** to create and check the package (scaffolding, metadata, lint, local testing).
2. **Node types:**
   - No duplicates of existing nodes; improvements to an existing node should be pull requests.
   - No logic or flow-control nodes.
   - **One third-party service per package.**
   - Trigger nodes may accompany the main node.
3. **Package source checks:**
   - The npm `repository` URL must match a public GitHub repo, and its links must work.
   - Author and maintainer details must be consistent between npm and GitHub.
   - README with usage examples.
   - **MIT license.**
   - **Published from a GitHub Action with npm provenance.** Required for verification submissions from **1 May 2026**; needs `@n8n/node-cli` ≥ 0.23.0.
4. **No external (runtime) dependencies.** The build guide's wording is "verified community nodes aren't allowed to use any run-time dependencies".
5. **Documentation.** README or API docs covering usage, example workflows and authentication.
6. **No access to environment variables or the file system.** All inputs come through node parameters and credentials.
7. **n8n best practices.** TypeScript, error handling and validation, and a clean linter run.
8. **English only.** This covers parameter names, descriptions, help text, errors and the README.

**Packaging basics:**

- The name must be `n8n-nodes-<name>` or `@<scope>/n8n-nodes-<name>`.
- The `n8n-community-node-package` keyword is required.
- Nodes and credentials must be registered under the `n8n` attribute of `package.json`.

**UX guidelines highlights** ([UX guidelines](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/ux-guidelines.md)):

- **Credentials and operations.**
  - Sensitive credentials are password fields.
  - Use CRUD vocabulary: Create, Create or Update, Delete, Get, Get Many, Update.
  - Use the Resource Locator, defaulting to "From list".
- **Output.**
  - Delete operations return `{"deleted": true}`.
  - Add a _Simplify_ toggle when a response has more than 10 fields.
  - AI tool nodes get an _Output_ parameter: Simplified / Raw / Selected fields.
- **Text conventions.**
  - Title Case for names; Sentence case for actions and descriptions.
  - Placeholders start with "e.g.".
  - Boolean descriptions start with "Whether…".
- **Errors.** Explain what happened and how to fix it, and include `[Item N]`. Avoid the words "error", "problem", "failure" and "mistake".

**Practical consequences for this package:**

- **Don't depend on `@redis-iris/agent-memory`** (rule 4). Also avoid bundling it: its environment-variable fallback could conflict with rule 6, and n8n's artifact scanner inspects bundled code (see the MongoDB thread in §6).
- **Don't depend on `@langchain/*`.** Couchbase's node was flagged for exactly this. Use `@n8n/ai-node-sdk` (§8) instead.
- **Expect a "duplicate" question** about the built-in Redis Chat Memory. The case for a separate node: a different service (Agent Memory rather than raw Redis), plus summarization, long-term memory and cross-session recall.

## 5. Naming

- **npm:** `@redis/n8n-nodes-agent-memory`.
  - `@redis` is Redis's own npm scope (`@redis/client`), which signals a first-party node and simplifies the author-consistency check.
  - The scope already says Redis, so the name doesn't repeat it.
  - "Agent Memory" matches the product name.
  - Alternatives:
    - `@redis-iris/n8n-nodes-agent-memory`: sits next to the SDK, but is less recognisable to n8n users.
    - `n8n-nodes-redis-agent-memory`: the fallback if nobody can publish under a scope.
- **GitHub:** `github.com/redis/n8n-nodes-agent-memory`. `repository.url` must point to this exact public repo, and the publish workflow must run from it, because provenance records the source repo.
- **Inside the package:**
  - Memory sub-node: "Redis Agent Memory". It appears next to "Redis Chat Memory", so the difference is clear.
  - Tools: "Redis Agent Memory Tool", or separate "Search Agent Memory" / "Save to Agent Memory".
  - Credential: "Redis Agent Memory API" (`redisAgentMemoryApi`).
- **Before publishing:** publish rights on the `@redis` npm scope are needed. The current `@redis/client` maintainers can publish or grant access.

## 6. Comparable vendor nodes

| Package | Vendor | Verified | Runtime deps | Notes |
|---|---|---|---|---|
| `n8n-nodes-qdrant` | Qdrant | **Yes**: an early adopter, on Cloud from n8n 1.94 | none | Full vector-search API (hybrid search, upserts, reranking) |
| `@pinecone-database/n8n-nodes-pinecone-assistant` | Pinecone | **Yes**: "built and maintained by our partners at Pinecone and verified by n8n" | none | Managed RAG: assistants, files, context snippets |
| `@mem0/n8n-nodes-mem0` | Mem0 | No: self-hosted only, per Mem0's docs | none | Memory CRUD and search; `usableAsTool`; no memory sub-node |
| `n8n-nodes-couchbase` | Couchbase | No: fails n8n's package scan | `couchbase`, `@langchain/*`, … | Self-hosted only unless redesigned |

MongoDB, Postgres and the existing Redis integrations ship inside n8n core (`n8n-nodes-base` / LangChain nodes) and never go through community verification.

**Database drivers can't be verified today.** A September 2026 thread on the n8n forum confirms that nodes needing a wire-protocol driver (the MongoDB driver requires `net`, `tls`, `dns`, `fs`) cannot pass verification:

- n8n staff wrote there is "currently no supported path".
- Bundling doesn't help, because the artifact scanner inspects the driver's internals.

Agent Memory is a REST API, so this doesn't affect this package. It would affect any node that talks to Redis directly.

**Built by third parties:**

- **Zep:** `n8n-nodes-zep-memory-v3` and several others. Memory sub-node; depends on Zep's cloud SDK.
- **Supermemory:** `n8n-nodes-supermemory`. Memory sub-node plus tool; no runtime dependencies.
- **Graphiti:** `n8n-nodes-graphiti`. Memory sub-node; depends on LangChain and others.
- **Self-hosted Mem0:** `n8n-nodes-mem0-self` plus about five other Mem0 forks.
- **Redis:** `n8n-nodes-memory-redis-isolated`. Redis chat memory with per-user isolation, built on `@n8n/ai-node-sdk`, but depends on `redis`.

**Takeaways:**

- Cognee is the reference implementation to copy: a verified vendor node with a memory sub-node and a tool node, zero dependencies, and the official AI SDK. Source: [topoteretes/cognee-integrations/integrations/n8n](https://github.com/topoteretes/cognee-integrations/tree/main/integrations/n8n).
- No database vendor has an official memory node, and there is no verified Zep or Mem0 memory sub-node. That is an opening for a first-party Redis node.
- **Caveat:** Cognee's _package_ is verified, but its memory sub-node only arrived in 0.7.0 (September 2026). Whether AI SDK-based sub-nodes pass review has not been confirmed with n8n.

## 8. Building a memory sub-node: `@n8n/ai-node-sdk`

`@n8n/ai-node-sdk` is n8n's SDK for AI nodes. It is published from the n8n monorepo, has existed since February 2026, and was at 0.32.x at the time of writing.

**How it is wired in:**

- **Package setup.** Declare it as a **peer dependency**, alongside `n8n-workflow`, and set `"aiNodeSdkVersion": 1` in the `n8n` block of `package.json`. n8n provides it at runtime, so the package keeps zero runtime dependencies.
- **Minimum n8n version.** 2.16, per Cognee's PR.
- **Scaffolding.** The CLI generates the skeleton: `n8n-node new <name> --template programmatic/custom-chat-memory`.

The pattern, as used in this repo's `nodes/RedisAgentMemoryChatMemory`:

```ts
class AgentMemoryChatHistory extends BaseChatHistory {
  getMessages()          // GET  /v1/stores/{storeId}/session-memory/{sessionId}
                         //      → events (+ optional summary as a system message)
  addMessage(message)    // POST /v1/stores/{storeId}/session-memory/events
  clear()                // DELETE /v1/stores/{storeId}/session-memory/{sessionId}
}

// in supplyData():
const memory = new WindowedChatMemory(history, { windowSize });
return supplyMemory(this, memory);
```

HTTP calls go through `this.helpers.httpRequestWithAuthentication`, using the credential's `authenticate` block (a bearer header).

## 9. Agent Memory vs. plain Redis in n8n workflows

Plain Redis in n8n gives the agent **storage**. Agent Memory gives it a **memory system**: it decides what to keep, compacts it and makes it searchable.

**What n8n users have with plain Redis today:**

- **Redis Chat Memory:** the last N messages of one conversation, stored as a list per session key with an optional expiry. Nothing carries over between sessions, and there's no search.
- **Redis Vector Store:** search over your own documents, but you build the pipeline yourself: chunking, embedding, upserting and deciding what to store.
- **Redis node:** raw commands; anything memory-like is hand-built.

**What Agent Memory adds:**

1. **Facts are extracted automatically.** Every chat turn is appended to the session, and the server pulls out lasting facts in the background. With plain Redis this needs an extra LLM step plus a vector upsert in every workflow.
2. **Long conversations are summarized.** A background job folds older turns into a summary, and `getSessionMemory` returns the summary plus the recent turns. Redis Chat Memory just cuts off old messages, so early context is lost.
3. **Memory works across conversations.** Long-term memories are tied to a user (`ownerId`), not a single session, so a new conversation can recall earlier ones.
4. **Search with filters.** Semantic search with a similarity cut-off and filters on owner, topic, memory type, namespace and date. This would otherwise be built by hand on the Redis Vector Store.
5. **Structure and scoping.** Hierarchical shared or private namespaces, custom memory types with typed attributes, and topic tags. This matters for multi-tenant n8n setups such as agencies.
6. **Memory that can be managed.** List, read, update, delete and move memories, which supports "forget me" requests, corrections and moderation. With Redis Chat Memory, workflows can only write.
7. **Memory shared beyond n8n.** The same store is reachable from Python, TypeScript and REST, so n8n agents and in-app agents can share user memory.

**Trade-offs:**

- **It's an extra service.** Users need an Agent Memory deployment (managed, or self-hosted on Redis) rather than a Redis connection string.
- **It costs model calls.** Extraction and summarization call a model provider, which is why the API has its own 424 error for provider failures.
- **Recall lags slightly.** Extraction is asynchronous, so a fact isn't searchable in the very next turn.
- **Users get less low-level control** than with raw Redis.

**Positioning.** Use Redis Chat Memory for short, single-conversation history, where it's cheap, fast and built in. Use Agent Memory when the agent must remember a user across conversations, stay coherent over long threads, or share memory with other applications. In node terms:

- the memory sub-node covers points 1–3 automatically;
- the action and tool node exposes points 4–7.

## 10. Recommendations and open questions

**Recommendations:**

1. **Package contents.** Ship two nodes plus one credential in this package:
   - **Redis Agent Memory**, the memory sub-node (scaffolded);
   - **Redis Agent Memory**, an action node with `usableAsTool` (to do). Resources: Long-Term Memory (Search, Create, Get, Get Many, Update, Delete, Move), Session (Get, Get Many, Delete, Add Event) and Namespace (Create, Get, Get Many, Update, Delete).
2. **No SDK or LangChain dependencies.** Use REST through n8n's request helpers, and use `@n8n/ai-node-sdk` for the sub-node.
3. **Pin to the REST contract**, not SDK versions. The API is young; 0.3 reworked namespaces.
4. **Release only through `.github/workflows/publish.yml`**, which provides provenance. Prefer npm Trusted Publishing (OIDC) over an `NPM_TOKEN`.
5. **Keep `n8n-node cloud-support` enabled** (strict mode) and keep `npm run lint` clean. That is the compliance check for Cloud verification.

**Open questions for n8n and Redis:**

- Do `@n8n/ai-node-sdk`-based memory sub-nodes pass verification today? (Cognee's 0.7.0 memory node suggests yes, but this is unconfirmed.)
- Should the "default memory" goal be pursued as a pull request to n8n core (where `memoryRedisChat` lives) instead of, or as well as, a community node?
- Who publishes under the `@redis` npm scope, and which GitHub organisation owns the repo?
- Session ID mode: should the node mirror n8n's built-in memory nodes ("Connected Chat Trigger Node" vs "Define below")?
- Should the sub-node also inject relevant long-term memories (a search on the latest user input) into the context, or leave that to the tool node?
